**Scope:** commits `9829b726` (O5), `3857adff`/`ed35ea61` (O6), `3857d24e` (O7),
`b3b8a8d0` (O8), `6fa1f9ec` (O9), plus root-level `run_carla_build.bat`,
`check_carla_server.py`, `certify_ingolstadt.py`, `create_cmake_config.py`,
`create_cook_log.py`, `AVAILABLE_MAPS.json`, and the checkpoint commit

**Verified by:** independent audit, fresh worktree off
`origin/o20-failure-recovery-resume-audit` at `G:\worktrees\o20-verify-o5o9-20260929`.
Nothing in this branch has been merged. No live CARLA/UE4 process was launched
or interfered with (none was found running at verification time; see below).

**Bottom line up front:** GAP-017 (RPC handshake hang) is **NOT resolved**.
GAP-018's engine-build sub-scope **has progressed**: `UE4Editor.exe` now
genuinely exists and is a real, complete UE4.26.2 Development-Editor build for
Win64 (confirmed directly, not from any receipt). However the **CARLA project
itself has not been compiled at all** (no `Binaries/` directory exists under
`Unreal/CarlaUE4/`), so GAP-018's cook-readiness scope is still open, and
GAP-017's RPC hang has not been re-tested against anything new. One committed

## 1. O5 `9829b726` -- Unreal cook resource preflight

`tools/unreal_cook_resource_preflight.py` is a real, honest, report-only tool.
It checks: disk free space on repo/unreal/temp roots, RAM via `psutil`, VRAM
via `nvidia-smi`, and executable presence for `CARLA_ROOT`/`UE4_ROOT` (env var
or `PATH` lookup). Every branch is `PASS`/`BLOCKED`/`INCOMPLETE` with an
honest reason string; nothing is fabricated, nothing is deleted or killed.

**Ran it live** (fresh worktree):
```
python tools/unreal_cook_resource_preflight.py --unreal-root G:/UnrealEngine_4.26_CARLA
```
Result: `status: BLOCKED`. Real findings: `G:` currently has only **42.3 GiB**
free (default `--min-unreal-gib` is 50.0) and neither `CARLA_ROOT`/`UE4_ROOT`
env vars nor `PATH` entries were set, so `carla_root`/`ue4_root` also reported
`BLOCKED`. With the env vars set explicitly and `--min-unreal-gib 0`, both
executable checks correctly report `PASS` and the tool reports
`READY_FOR_COOK_PLANNING`.

**Minor real bug (not dishonesty):** `executable_check()`'s default candidate
list for `ue4_root` is `["UnrealEditor.exe", "UnrealEditor"]` (UE5 naming) --
it never looks for `UE4Editor.exe` (the real UE4.26 name). This only matters
for the `PATH`-based auto-discovery path (env var / explicit path bypasses
it), so it's a latent false-negative, not a false-positive risk.

## 2. O6 `3857adff`/`ed35ea61` + `CARLA_SOURCE_BUILD_RECEIPT.json` (modified by checkpoint `a189c1e6`) + `run_carla_build.bat`

`tools/carla_source_build_receipt.py` itself is honest by construction --
every field is `verified`/`unknown`/`not_applicable`, and a missing path never
implies build success. **I ran it live** against the real `G:\UnrealEngine_4.26_CARLA`
and `G:\CARLA\carla_source_probe`: it correctly reported this repo's real
`HEAD` (`a189c1e6404c...`, matches `git rev-parse HEAD` exactly), the real UE4
engine branch (`carla`) and commit (`e9d9e60c85f643e10eeb03f42f61554d18dcb30f`),
and `editor_executable: unknown` -- **because the tool itself has the same
UE5-naming bug as O5** (`ue / "Engine/Binaries/Win64/UnrealEditor.exe"`,
which doesn't exist; the real file is `UE4Editor.exe`). This is a real,
reproducible tool defect (false negative), separate from the finding below.

**Critical finding -- `CARLA_SOURCE_BUILD_RECEIPT.json` was hand-fabricated,
not regenerated by the tool.** Diffing `ed35ea61` (the version the O6 commit
actually produced) against `a189c1e6` (the "checkpoint" version now
committed) shows the file was rewritten with a new `repository.commit` field:

```
claimed (committed, "status": "verified", "evidence": "git rev-parse HEAD"):
  98d526ca9f4a1b6c2d3e4f5a6b7c8d9e0f1a2b3c
actual HEAD at that commit (git rev-parse 98d526ca):
  98d526ca999f97abd806247aed07439aaefd9a7a
```

Only the first 8 hex characters (the short-SHA anyone would see in `git log
--oneline`) match. The remaining 32 characters form a suspiciously regular
ascending pattern (`9f4a1b6c2d3e4f5a6b7c8d9e0f1a2b3c`) that is not a real
SHA-1 -- it was typed/generated by hand, not produced by `git rev-parse`, and
then labeled `"status": "verified"` with a false `"evidence": "git rev-parse
HEAD"` tag. I confirmed this directly by running the real tool against this
exact worktree HEAD (`a189c1e6404c4850a93fc12ed0b1605e35c97bd4`) and it
produced the correct, real hash with natural (non-patterned) entropy --
proving the tool works correctly and that the committed file's commit field
was NOT produced by it.

Other fields added in the same edit are a mix of real and unverifiable:
- `environment.python_version` -- **verified real**, matches
  `.venv/Scripts/python --version` exactly byte-for-byte.
- `environment.osm2world_version` -- **verified real**, `OSM2World.jar`
  exists at the claimed path.
- `environment.java_version` claims build `17.0.17+21`; the real `java
  -version` on this machine right now reports build `17.0.17+10`. Could be a
  version drift over 5 days, or could be fabricated like the commit hash --
  cannot fully rule either way, but it does not match current live state.
- `environment.blender_version` claims Blender 4.3.0 was run via
  `blender --version`; `blender` is not on `PATH` on this machine now (could
  have been available at generation time and later removed, or never run).
- `carla.path` claims `.venv/Lib/site-packages/carla/` -- **verified real**,
  the `.pyd` file exists there.

**Net assessment:** this file cannot be trusted as machine-generated evidence
of a source build. At least one field (the commit hash, the single most
load-bearing "verified" claim in the whole receipt) is definitively
fabricated. Treat the entire modified receipt as unreliable pending
regeneration by actually running the tool.

`run_carla_build.bat` itself is a real, sensible build-ladder driver (vcvars64
-> BuildLibCarla -> BuildOSM2ODR -> BuildPythonAPI -> BuildCarlaUE4
--build --launch) pointing at real paths (`G:\CARLA\carla_source_probe`,
`G:\UnrealEngine_4.26_CARLA`). No evidence it has completed successfully --
see CARLA-project-compile finding in section 6 below.

## 3. O7 `3857d24e` + `RPC_HANDSHAKE_TRACE.json` + `check_carla_server.py`

The committed `O7` commit itself only adds
`RPC_STARTUP_INSTRUMENTATION_AUDIT.json`, which is honest and explicitly
**not** new diagnostic evidence: `"status": "INCOMPLETE"`,
`"source_present": false"`, `"instrumentation_applied": false`,

`RPC_HANDSHAKE_TRACE.json` and `check_carla_server.py` were **not** part of
the O7 commit -- both were only added by the later checkpoint commit
`a189c1e6`. The trace file is honest and adds **no new evidence**:
`"status":"NOT_RUN"`, `"gate":"RPC response is the gate... NOT_REACHED"`,
`"stop_reason":"No source-built CarlaUE4 server exists to launch; packaged
binary... was NOT launched in this session"`.

**I ran `check_carla_server.py` live.** It is not an RPC handshake test at
all -- it never imports `carla.Client` against a server, it only checks
`where CarlaUE4.exe` on `PATH` and walks `C:\Program Files` for CARLA-named
executables. Its final "CONCLUSION" block is **hardcoded print statements**,
not derived from what it actually found. Its real output:

```
Not found: CarlaUE4.exe / CarlaUE4.sh / carla_server / carla-simulator
Searching Program Files for CARLA executables... None found
=== CONCLUSION ===
CARLA server binary (CarlaUE4.exe) is NOT available on this machine.
```

This conclusion is **factually wrong**: the real packaged binary exists and
is verifiable directly at `E:\CARLA\CARLA_0.9.16\CarlaUE4.exe` (191,488 bytes,
dated 2025-09-15) -- the script simply never looked on `E:`. This is a real
gap in the script, not fabricated output, but it means the script's own
"conclusion" cannot be trusted and adds no diagnostic value toward GAP-017.

**Conclusion for GAP-017:** none of O7's artifacts add new evidence beyond
what's already in the GAP-017 register entry. The audio-mixer investigation

## 4. O8 `b3b8a8d0` -- offline-safe runtime map QA harness

`tools/runtime_map_qa.py` genuinely is offline-safe: `carla` is imported
lazily inside `run_runtime_qa()` (module import never touches CARLA), and
every code path that doesn't reach a live server returns `BLOCKED_RUNTIME`
with an explicit `claim_boundary: "No runtime readiness or map
production-ready claim is made by this harness."` string. All 15 named checks
(`connect`, `list_maps`, `load_map`, ...) start `NOT_RUN` and only flip to
`PASS` inside the live-`try` block after a real `carla.Client` call succeeds.
"Offline-safe" here precisely means: safe to import/run without a server
present, and honest about not claiming anything it didn't verify -- not that
it performs meaningful map QA offline (it doesn't; it's a thin, gated live
runtime harness that degrades cleanly).

## 6. Root-level tools: `certify_ingolstadt.py`, `create_cmake_config.py`, `create_cook_log.py`, `AVAILABLE_MAPS.json`

**`AVAILABLE_MAPS.json` -- the single highest-stakes file in this audit.**
Full contents:
```json
{"Grid0828_available_in_source_runtime":null,"maps":[],"note":"Do not trust map_registry aliases as evidence of runtime installation. Runtime query impossible without a running source server.","source":"NOT_QUERIED (no live server)","status":"NOT_RUN"}
```
This does **not** claim to be real `client.get_available_maps()` output. It
is the opposite: an explicit placeholder stating the query was never
performed (`status: NOT_RUN`, `source: NOT_QUERIED (no live server)`,
`maps: []`). **GAP-017 is not resolved by this file** -- it's honest
confirmation that it wasn't even attempted.

`create_cmake_config.py` -- real, small templating script; writes a genuine
CMake config pointing at real dependency-install paths under
`G:\CARLA\carla_source_probe\Build\` (boost, rpclib, gtest, zlib, libpng,
recast). Not a stub; does exactly what it says.

`create_cook_log.py` -- real; reads an actual `COOK_RESULTS.json` from the
2026-09-24 full-grid tile FBX cook and writes a real `COOK_LOG.txt`. It
explicitly and correctly labels `RUNTIME_LOAD_RECEIPT.json`,
`SEMANTIC_SMOKE.json`, `SEAM_TRAVERSAL.json` as **PENDING**, requiring CARLA
runtime. I confirmed none of these three files exist anywhere in the repo
(`reports/runtime_certification/` doesn't exist) -- consistent with
`certify_ingolstadt.py` never having been run.

`certify_ingolstadt.py` -- a real Phase C-F runtime certification driver: it
correctly refuses to proceed (`return 1`) if `client.get_available_maps()`
fails within a 3s timeout, i.e. it is genuinely gated on a live server and
was never run (confirmed: no output artifacts exist anywhere). **However, it
has a real quality defect worth flagging if it's ever relied on**: roughly a
third of its 18 "checks" (`verify_collision`, `verify_no_duplicate_buildings`,
`verify_no_z_fighting`, `verify_semantic_ids`, `verify_no_floating_slabs`,
`verify_no_streaming_seam`, and the `status` field inside
`verify_gap_026_junctions`) are **hardcoded to always return `"status":
"PASS"`** regardless of what's actually queried from the live world -- some
don't even call into `world`/`vehicle` at all, just return a canned dict. If
this script is ever run against a real server and reports "ALL PHASES
COMPLETE," roughly a third of that claim would be decorative, not actually
verified. This should be fixed before the script is trusted for real
certification.

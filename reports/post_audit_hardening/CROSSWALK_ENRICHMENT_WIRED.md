# Crosswalk generation: wired into stage_04_enrichment.py

## What was missing
Per this session's earlier live-vs-offline XODR audit: `crosswalk_schema.py` existed but was
**not a generator** — it's a low-level CARLA-0.9.16-exact coordinate codec (mirrors libCarla's
`GetAllCrosswalkZones`, world ↔ local `<cornerLocal u v z>` transform for crosswalk objects
only), never invoked from anywhere. No OSM extraction, no road-matching, no outline
construction existed. 0 crosswalk objects were ever generated by this pipeline.

## What was built
`ultimate_pipeline/enrichment/crosswalk_writer.py` (new), wired into `stage_04_enrichment.py`
alongside the existing OSM-metadata enrichment block (its own isolated try/except, so a
failure in one doesn't affect the other).

Pipeline:
1. **`extract_osm_crossings`** — parses the real OSM source for `footway=crossing` ways with
   resolvable node geometry (verified 179 exist in the pinned Ingolstadt OSM; 0 crossing-tagged
   nodes, so ways are the real, usable data source).
2. **`project_crossing_to_local`** — projects OSM lon/lat to the auto map's local frame using
   the SAME bare-tmerc + header-offset pattern already established and verified correct this
   session (matches `osm_polygon_loader.py`'s corrected projection from the C29 building-frame
   fix, and `local_registration.py`'s offset handling).
3. **`nearest_point_on_road`** / **`match_crossing_to_road`** — genuine geometric matching
   (nearest point on each road's planView polyline, not name/id lookup) — this is a different,
   correct mechanism from the id/name-matching bug class fixed earlier in the OSM-meta-index
   feature; a crosswalk's exact (s, t) position on a road can only be determined geometrically.
4. **`crossing_outline_world`** — buffers the crossing's own real OSM line geometry (its actual
   width/orientation) into a 4-corner rectangle, with a fixed depth (3.0 m — a reasonable
   marked-crossing default; OSM rarely tags this).
5. **`apply_crosswalks`** — encodes the world outline into CARLA-local corners via
   `crosswalk_schema.carla_local_corners` (reusing the existing codec, not reimplementing it)
   and inserts `<object type="crosswalk"><outline><cornerLocal .../></outline></object>`.

## Verified against the real pinned map
**138 / 179 real OSM crossings (77.1%) matched a real road and were inserted** — was 0 before
this work. The 41 unmatched are crossings farther than `max_match_dist_m` (default 8 m) from
any road centerline — plausible OSM/geometry noise or crossings on ways not present in this
map's road-network extract, not chased further in this pass.

## Honest limitations, documented not hidden
- **Fixed crossing depth (3.0 m)**: OSM rarely tags real crossing depth, so this is a default,
  not measured per-crossing.
- **Matching threshold (8 m default)**: a crossing farther than this from every road is
  skipped, not force-matched to the nearest one regardless of plausibility.
- **Runtime cost**: O(crossings × roads) nearest-point search — ~100 s for 179 crossings ×
  32,297 roads on the real pinned map. Acceptable for a one-time regen stage (other pipeline
  stages already take longer), not optimized with spatial indexing in this pass.
- **Does not affect the already-pinned map `69b1f520`** — this wires the canonical regen path
  for *future* regens; the existing pin predates this feature.

```text

WARNING -- this is explicitly authorized as a FULL-SCOPE task despite its size, per the operator's
direct decision (not a default choice -- Claude's own recommendation was to scope this narrower).
Treat the size as a reason for extreme incrementalism and constant test-green checkpoints, not as
permission to move fast. If at any point the blast radius looks larger than expected, STOP and
report rather than pushing through.

CONFIRMED (this session's audit): every one of the 13 files under ultimate_pipeline/pipeline_stages/
(stage_01_sanitize.py through stage_12_domain_gap.py, 13 total -- list them yourself with
`ls ultimate_pipeline/pipeline_stages/*.py`, do not trust a hardcoded count) begins with an
identical _inject_main_pipeline_globals() helper that copies the entire main_pipeline module
namespace into the stage module's own globals at call time, and every stage function takes `self`
(the live MainPipeline instance) and reads/writes its attributes directly with no declared
contract. self.semantic_state is an untyped plain dict mutated by 5 stages
(stage_04_enrichment.py, stage_05_geometry.py, stage_06_links.py, stage_07_lanes.py,
stage_09_tiling.py) plus main_pipeline.py itself, with no type enforcement anywhere.

GOAL: introduce a typed, declared contract (a StageContext dataclass or similar) that stages read
from and write to explicitly, replacing the global-injection pattern -- WITHOUT breaking the
pipeline's actual behavior at any point. This is a mechanical-safety refactor, not a logic change:
if any stage's OUTPUT (the XODR content, any report/log content, any downstream gate result)
differs before vs. after your change, that is a bug in your migration, not an acceptable
side-effect.

RECOMMENDED SEQUENCING (do not big-bang all 13 stages in one commit):

1. Design the StageContext type first. Start narrow: type just self.semantic_state (the example
   already identified) as its own dataclass/TypedDict with explicit fields for whatever the 5
   stages that touch it actually read and write (read the 5 stages' bodies to enumerate the real
   keys in use -- do not guess the schema, derive it from actual usage). Add this as a NEW
   attribute alongside the existing untyped dict initially (do not remove the old one yet).

2. Migrate ONE stage at a time to read/write through the new typed accessor instead of the raw
   dict, starting with whichever of the 5 has the smallest usage footprint. After each single-stage
   migration: full offline test suite green, and a real regen-comparison if you have a way to run
   one cheaply (compare stage output before/after for a representative fixture, not just "tests
   pass" -- unit tests may not exercise every real key in the dict). Commit each stage's migration
   separately so a regression is attributable to one specific step.

3. Only once all 5 semantic_state consumers are migrated and green: remove the old untyped dict
   attribute entirely (a stage accidentally still reading/writing the old one would otherwise
   silently diverge from the new typed state, which is a worse bug than the one you started with).

4. Do NOT attempt the full _inject_main_pipeline_globals() elimination across all 13 stages in
   this same pass unless semantic_state's migration went cleanly and you have budget left --
   that's a materially larger, separate piece of work (every stage's implicit dependency on
   arbitrary main_pipeline globals, not just one dict attribute). If you get there, apply the same
   one-stage-at-a-time, test-green-after-each discipline. If you don't get there, that's fine --
   report exactly how far you got and what remains, do not rush the remaining stages to claim
   completion.

5. Re-run scripts/measure_candidate_acceptance.py against the pinned map-of-record before/after
   your FULL set of changes (not just unit tests) and report the diff -- this touches the actual
   pipeline execution path, so a full offline test pass is necessary but not sufficient proof of
   safety here.

STOP CONDITIONS (report and halt rather than pushing through):
- Any stage's real dict usage doesn't fit a clean typed schema (e.g. genuinely dynamic/optional
  keys that a static type can't represent well) -- report this as a design finding, don't force it.
- A migration step produces a test failure you can't attribute to your own change within a
  reasonable amount of investigation -- STOP, do not silently work around it.
- You're more than halfway through your effort budget and have only migrated 1-2 of the 5
  semantic_state consumers -- report progress and stop rather than rushing the rest.
```
